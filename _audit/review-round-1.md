# github-release/ Review — Round 1

Three reviewer personas pass. Each finding is tagged CRITICAL / MAJOR / MINOR.

---

## Persona A: Non-technical career changer

A nurse who has been on the same ward for twelve years and is moving into hospital administration. They have never written a "structured CV." They have never opened a JSON file. They have no idea what `git` is and they will never touch a terminal.

### A1. CRITICAL — `profile.md` "Identity" section uses formatting they will not understand

The onboarding files produce `profile.md` with structures like:

```
- **r1** | Designed and delivered the company-wide technology strategy aligned to business growth and regulatory expectations.
```

A non-technical reader sees `**r1** |` and assumes it is a typo or template debris. They do not know it is a stable ID for the system to reference. If they edit the file directly to clean it up, they delete the IDs and the next apply.md run silently fails to reference responsibilities correctly.

**Fix:** The onboarding files must explain in a one-line comment what the IDs are for, and tell users not to delete them. The ID prefix should also use a less alarming syntax (e.g. `[id: r1]` rather than `**r1** |`).

### A2. MAJOR — `apply.md` says "paste the JSON" with no explanation of what JSON is

`apply/apply.md`'s hand-off says "Paste the JSON above." A non-technical user does not know what JSON is, what "above" means, or how to "paste" a code block from one Claude conversation to another.

**Fix:** Add a "How to copy a code block from a Claude response" sentence in USAGE.md and reference it in apply.md. The sentence is one paragraph: click the copy button at the top of the code block, paste into the next Claude conversation.

### A3. MAJOR — README references "Cowork mode" without explaining how to turn it on

USAGE.md explains what Cowork mode is, but README.md says "works in any Claude conversation (the desktop app, the CLI, claude.ai, Cowork mode)" without saying how to enable Cowork. A user reading README first will get stuck on this.

**Fix:** Either remove "Cowork mode" from README's plain-language list (it can stay in USAGE) or add a one-sentence "What is Cowork mode" link.

### A4. MAJOR — "Save the file with the exact filename" is harder than it sounds on Windows

USAGE.md mentions Notepad's default `.txt` extension. Good. But it does not warn that Word, Google Docs, and other rich-text editors will save Markdown files with hidden formatting that breaks the toolkit. A user who opens `voice.md` in Word and saves it gets a file the toolkit cannot read.

**Fix:** Add a "Editors that work" / "Editors that do not work" list in USAGE.md.

### A5. MINOR — "Compensation floor" assumes the user has set one

The filter onboarding asks for compensation floor. A non-technical career changer might genuinely not know what they are worth. The prompt should say it is OK to leave this blank.

**Fix:** Onboarding section 8 can add "If you do not have a number in mind, that is fine — leave it blank for now."

### A6. MINOR — Reading order of files is not documented

A new user receives README, USAGE, CONTRIBUTING. They do not know which to read first. README is the entry point but does not say "next, read USAGE" or "skip CONTRIBUTING unless you want to add to the toolkit."

**Fix:** README.md should end with a one-line "Next: read USAGE.md if you want the step-by-step." CONTRIBUTING.md should open with "If you are using the toolkit and not contributing to it, you can skip this file."

## Persona B: Consistency auditor

A reviewer who runs the same profile + same JD twice and looks for any difference in the output.

### B1. CRITICAL — Cover letter date is generated by Claude, not derived

`apply.md` says "the cover letter date is in the date_format from format.md." But Claude generates the date string from "today's date." Two runs on the same day produce the same date; runs across the day boundary produce different dates. More importantly, "today's date" is interpretive — the model may use the conversation's context, the system clock, or a hallucination.

**Fix:** Either (a) the prompt instructs Claude to always pull the date from the user-supplied input, or (b) the artifact JS renders the date dynamically using the format spec from a single fixed date the user supplies. Option (b) is the consistent choice. Add a `date` field that the user passes through in the application JSON, generated once at apply time and rendered as-is by the artifact.

### B2. CRITICAL — CV artifact uses only one margin value for all four sides

In `cv-artifact.md`'s `applyFormat`:

```js
if (fmt.margin_top_inches != null) root.setProperty("--page-padding",
  Math.max(fmt.margin_top_inches, fmt.margin_left_inches || 1) * 25.4 + "mm");
```

If the user specifies asymmetric margins (top 0.5, sides 1.0, bottom 0.7), they all collapse to a single value. Two users with intentionally different margin specs get identical output.

**Fix:** Apply each margin separately as `--page-padding-top`, `--page-padding-right`, `--page-padding-bottom`, `--page-padding-left`. Update the `.page` rule to use all four.

### B3. MAJOR — Voice tripwire's "sentence pattern" matching is interpretive

`apply.md` says: "If a prohibition is a sentence pattern ('Never start a bullet with was responsible for'), match the literal pattern at the start of any bullet or sentence." But what counts as "the start of a bullet" depends on parsing the prose. Two runs may parse differently.

**Fix:** Distinguish between two prohibition types in voice.md:
- Phrase prohibitions: literal substring, case-insensitive.
- Pattern prohibitions: regex, written by the user, with escaping documented.

Pattern prohibitions are advanced; default to phrase. Document this clearly.

### B4. MAJOR — `format.md` schema mismatch tolerated silently

`apply.md` says to use defaults if the format.md spec block is missing or fails to parse. But it also says "warn the user once." The "once" is interpretive — the same Claude session running multiple applies may warn or not warn. And the user has no log to inspect after the fact.

**Fix:** Always include a `format_status` field in the JSON: `"loaded"`, `"defaults_used"`, or `"partial"`. The artifact can show a banner (or the user's apply transcript shows the field). Two runs on the same input always produce the same status.

### B5. MAJOR — Section heading text hard-coded in CV artifact JS

The artifact has hard-coded section titles ("Professional experience", "Education and executive development", "Awards and recognition", "Volunteering and community"). The format spec has no `section_titles` field. So if the user wants their CV in another language, or wants "Education" rather than "Education and executive development," they cannot achieve it without editing the artifact. Cross-locale consistency breaks.

**Fix:** Add `section_titles` to the format spec, default to the current English titles, allow override.

### B6. MAJOR — Stable ID format is not enforced

Onboarding tells users to use lowercase-with-dashes IDs. There is no validator. A user who runs onboarding twice (same career, same answers) may get IDs `r1, r2, r3` first time and `resp-1, resp-2, resp-3` second time. Subsequent applies that reference older IDs break silently.

**Fix:** Lock the ID convention in the onboarding output instructions: `r1, r2, ...` for responsibilities; `<verb>-<noun>` (lowercase-with-dashes) for achievements. Add a one-line check at the end of onboarding: "Confirm: every responsibility ID is `r1, r2, r3, ...` and every achievement ID is two-or-three-word lowercase-with-dashes."

### B7. MAJOR — `fit-assessment.md` and `apply.md` Step 1 are not literally identical

`apply.md` Step 1 and `fit-assessment.md` are described as the same prompt. They are similar but not byte-identical. A reviewer running both gets two different fit assessments for the same input.

**Fix:** Either keep one canonical fit-assessment prompt and have apply.md `## Step 1` say "run the fit-assessment.md prompt at this point and pass the result to me," or keep both inline copies but add a CI-style assertion that the relevant block in each file is identical.

### B8. MINOR — `bullet_target_words` is in the spec but no renderer enforces it

The spec has `bullet_target_words` (e.g. 70 for executive). Neither the apply prompt nor the artifact does anything with it. It is documentation, not enforcement.

**Fix:** apply.md should warn if a bullet is more than 1.5x the target and if a bullet is less than 0.5x the target. The artifact can ignore it (it is content, not layout).

## Persona C: International senior candidate

A CFO in Germany, a head of product in Singapore, a partner at a consulting firm in Canada. Their CV conventions, page-length norms, personal-information expectations, and hiring-market signals are all different.

### C1. CRITICAL — Photo support documented but not implemented

The format spec has `include_photo: true|false`. Onboarding sets it to `true` for German, Swiss, and Austrian markets. But the CV artifact has no photo rendering anywhere. A German user sets `include_photo: true`, generates a CV, and gets the same photoless layout as the UK user. The market-specific feature is decorative.

**Fix:** Add a `header.photo_url` field to the JSON (data URL or external URL) and render it in the CV artifact when `include_photo: true`. Photo placement: top-right of the header block, square crop, 30mm × 30mm.

### C2. CRITICAL — Personal details (DOB, nationality, marital status) are documented but not implemented

Same problem as photo. `include_personal_details: true|false` is in the spec. Onboarding asks the question and sets it. The artifact ignores it. A German CV needs DOB, place of birth, nationality, and (sometimes) marital status. None of these have a place in the schema or in the artifact.

**Fix:** Add to the JSON:
- `header.personal_details.date_of_birth`
- `header.personal_details.nationality`
- `header.personal_details.marital_status`
- `header.personal_details.place_of_birth`

Render them in the artifact when `include_personal_details: true`, in the header block, in the user's spelling. Add the corresponding fields to `profile.md`'s Identity section as optional.

### C3. MAJOR — Section names are hard-coded in English

Already flagged as B5. From a German or French candidate's perspective this is a CRITICAL issue: their CV is in English even when they want it in German or French. The hard-coded titles cannot be overridden.

**Fix:** Same as B5. Add `format.section_titles` (a map of section_key to display string).

### C4. MAJOR — Date format is interpretive

`format.date_format` says "MMM YYYY" or "January 2023 - Present" or "01/2023 - heute". The CV artifact does not parse dates; it renders whatever string is in `roles[].dates`. So consistency depends on the user (or apply.md) writing the date in the right format. Two runs of the same profile.md (with dates in YAML form) could produce two date strings.

**Fix:** Either the apply prompt is responsible for normalising dates to the spec format before producing the JSON, or the format spec is treated purely as a hint and dates are always rendered as-written. The current state is the worst of both: a config that suggests precision without delivering it.

Decision: dates render as-written in `profile.md`. The format spec keeps the field for documentation only. Document this clearly in CONTRIBUTING.md and onboarding.

### C5. MAJOR — Sample sentences in voice tests are UK/NZ-biased across all three onboarding files

For a Singapore senior tech leader or a German finance head, the example sentences (A/B/C) read awkwardly in their working register. The choice between "I rebuilt the technology function" and "Transformed the technology function into a strategic, board-trusted capability" maps onto British corporate vs Anglo-American consultancy English. A German exec would speak in a different register entirely; the choice is not meaningful for them.

**Fix:** The onboarding prompt should ask, after the market question, to either (a) use the default UK/NZ sample sentences if the user is comfortable with them, or (b) provide their own three sample sentences in the register they actually use.

### C6. MAJOR — "Languages spoken" is missing for European and Asian senior CVs

Multilingual ability is a major signal in Switzerland, Singapore, the EU, and parts of Africa. The schema has no place for it.

**Fix:** Add `header.languages` (a list of `{ language: "...", level: "Native | Fluent | Working | Basic" }`) and a `languages` section that the artifact renders when present and `format.section_order` includes it.

### C7. MINOR — "Education and executive development" is a senior-leader UK phrase

For a Singapore early-career or a German technical lead, "executive development" is jargon. The default section title for `education` should be "Education" plain. The exec onboarding can override to "Education and executive development."

**Fix:** Default to "Education." Override in the executive onboarding's format.md.

### C8. MINOR — Phone number format

The example profile uses `+44 7700 900123`. UK style. A German user would write `+49 30 12345678`; a French user `+33 1 23 45 67 89`. Onboarding does not ask for a preferred format.

**Fix:** Onboarding section 0 (after market) can prompt the user to enter their phone number in their market's standard format. The toolkit renders verbatim.
